# kcore correctness and C++ guidelines audit

What this repo does: kcore provides shared C++23 types, error handling, containers,
filesystem access, serialization, threading, logging, and profiling. This audit
assumes a library reused by macOS/Linux applications with several worker threads,
ordinary configuration input, and repeated creation/destruction of objects.

Reviewed revision: [`1c9a829`](https://github.com/nekoffski/kcore/commit/1c9a829797d4aebbaf2548e5045513359b3620c5),
30 October 2026. All **28 public headers and 15 implementation files** were read,
together with all library tests, package-consumer tests, README, and build/package
configuration. No library or application code was changed.

The C++ Core Guidelines are recommendations, not an ISO conformance certificate.
The findings below distinguish demonstrated failures from interface-contract risks.
“Must fix” means before relying on the affected facility under the stated usage;
it does not mean every existing Anchor execution triggers the issue.

## Evidence and scope

- **83 existing kcore tests pass** in the default Debug configuration.
- Targeted AddressSanitizer probes reproduced use-after-free during derived-thread
  destruction and active-thread moves, use-after-scope in `UniqueInstance`, and a
  dangling reference returned by `MoveOnlyFunction`.
- Targeted ThreadSanitizer probes reported **four data races**: `IdLake`, UUID
  generation, profiler collection, and logging-level state.
- Runtime probes confirmed numeric environment parsing errors, an escaping JSON
  exception, a swallowed read failure, stale signal masks, invalid profiler
  durations, termination on a second `start()`, a null callable crash, and
  termination from an underlying throwing hash.
- Compile probes confirmed failures in `ThreadPool::submit`, lazy evaluation,
  `unwrap<void>`, and compound enum operator reference semantics.
- A separate profiling-enabled build succeeds, but
  `Profiler.DisabledInstrumentationReportsItsState` fails because it always
  expects `false`. That test needs to follow the selected configuration when
  addressing profiler coverage.
- The temporary probe harness instrumented kcore itself; these were targeted
  probes, not a sanitizer run of the entire existing suite. The harness and raw
  logs were temporary local artifacts; concrete triggers and observed outcomes
  are preserved in the findings below. Some sanitizer stack frames could not be symbolized
  in the sandbox; the reports still identify the failing operations/functions.

Primary references: [C++ Core Guidelines](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines),
especially CP.2, R.1/R.12, C.35/C.36, F.6, C.160, and T.10;
[nlohmann JSON parse exceptions](https://json.nlohmann.me/api/basic_json/parse/).
Rule references identify the relevant design concern; the failure evidence comes
from this library's code and the probes.

## Must fix before relying on the affected facilities

### 1. Joining in the base destructor happens after derived state is destroyed

Location: [Thread.cpp:10](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/src/runtime/Thread.cpp#L10).

- **What this is:** `Thread` owns a worker that runs the derived class's `run()` method.
- **Problem:** C++ destroys derived members before entering `Thread::~Thread()`. A worker that is still using those members can read freed memory before the base destructor joins it; a latch-controlled probe produced an AddressSanitizer heap-use-after-free.
- **Fix:** Make stop/join happen at the beginning of every derived destructor and make that requirement explicit, or move thread ownership to composition so shutdown precedes destruction of worker state. A base destructor alone cannot enforce this ordering. Relevant rules: R.1 and C.36.
- **If we skip it:** New consumers with an ordinary default derived destructor can crash during shutdown. Existing Anchor services that explicitly stop/join before member teardown avoid this particular trigger.

### 2. Moving a running Thread leaves its callback pointing at the old object

Locations: [Thread.cpp:12](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/src/runtime/Thread.cpp#L12),
[Thread.cpp:40](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/src/runtime/Thread.cpp#L40).

- **What this is:** Public move operations transfer the `std::thread` handle between objects.
- **Problem:** The running lambda captured the original `this`; moving its handle does not change that capture. Moving a started worker and destroying its source produced an AddressSanitizer heap-use-after-free.
- **Fix:** Restore non-movability for this inheritance-based thread type. If inactive workers must be stored in a container, keep them at stable addresses, for example behind `unique_ptr`; supporting active moves needs a different ownership model.
- **If we skip it:** A container relocation or explicit move can leave a live worker executing through a destroyed object.

### 3. MoveOnlyFunction accepts callables that return dangling references

Locations: [Functional.hh:41](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/include/kcore/Functional.hh#L41),
[Functional.hh:63](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/include/kcore/Functional.hh#L63).

- **What this is:** The callable wrapper checks whether a callable can produce the requested return type.
- **Problem:** `MoveOnlyFunction<const int&()>{[] { return 42; }}` is accepted, but the returned reference points to a destroyed temporary. AddressSanitizer reproduced a stack-use-after-return. A typed null function pointer is also accepted as a truthy callable and then crashes on invocation.
- **Fix:** Reject reference results that bind a temporary, and normalize null function/member pointers to the empty state. Delegate to `std::move_only_function` when all supported toolchains provide it; this audit's Apple libc++ does **not** provide it, so an immediate alias replacement would not build. Relevant concern: T.10 and lifetime safety.
- **If we skip it:** A callable that passes the wrapper's constraints can cause undefined behavior. The existing empty-call assertion does not catch either case.

### 4. UniqueInstance retains a pointer after its object has died

Location: [Singleton.hh:21](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/include/kcore/Singleton.hh#L21).

- **What this is:** `UniqueInstance<T>` stores the address of the one permitted object.
- **Problem:** Construction sets `s_instance`, but destruction never clears it. Access after the object's scope ends produced AddressSanitizer stack-use-after-scope; constructing a later replacement would also trip the “already exists” assertion.
- **Fix:** Clear the registered pointer as part of destruction and define whether construction/access must be confined to one thread. If concurrent use is required, pointer publication and object lifetime need synchronization. Relevant rule: R.1.
- **If we skip it:** The helper can expose dead objects or permanently reject a valid replacement after the first instance is destroyed.

### 5. IdLake protects the pools but not the map containing them

Location: [Id.hh:26](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/include/kcore/Id.hh#L26).

- **What this is:** `IdLake` chooses a shared `IdPool` by C++ type.
- **Problem:** `s_pools[typeid(T)]` can insert and rehash the shared map without a lock. The mutex inside `IdPool` is acquired only after that access; simultaneous allocations produced a ThreadSanitizer race in map rehashing.
- **Fix:** Use a function-local static `IdPool` per template type, shared by acquire/release, or protect every lookup/insertion of the map. The per-type static removes the map entirely. Relevant rule: CP.2.
- **If we skip it:** Concurrent first use can corrupt the registry or lose allocations despite each pool having a mutex.

### 6. UUID generation shares an unsynchronized random engine

Locations: [Random.cpp:8](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/src/Random.cpp#L8),
[Random.hh:18](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/include/kcore/Random.hh#L18).

- **What this is:** `RandomEngine::get().uuid()` and `WithUuid` use one mutable generator.
- **Problem:** Singleton initialization is thread-safe, but subsequent generator calls are not synchronized. Four threads generating UUIDs produced a ThreadSanitizer race inside the random engine.
- **Fix:** Protect generation with a mutex, or deliberately use a generator per thread. Keep the distinction between UUID generation and cryptographically secure token generation explicit. Relevant rule: CP.2.
- **If we skip it:** Concurrent identity generation has undefined behavior; uniqueness and engine state are no longer reliable.

### 7. Profiler snapshots race with event recording

Locations: [Profiler.cpp:34](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/src/Profiler.cpp#L34),
[Profiler.cpp:46](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/src/Profiler.cpp#L46).

- **What this is:** Workers append begin/end events while `generateSummary()` reads and clears their buffers.
- **Problem:** The profiler mutex protects the registry and summary path, but `RegionTimer` writes through a cached vector reference without that mutex. Concurrent recording and summary generation produced a ThreadSanitizer race in summary processing.
- **Fix:** Synchronize readers and writers of each event buffer and define a safe snapshot operation. A “join every worker before collecting” precondition is an alternative only if that restriction is acceptable and enforced/documented. Relevant rule: CP.2.
- **If we skip it:** Collecting a live service's profile can race with vector allocation, iteration, or clearing and corrupt memory.

### 8. The logging wrapper introduces its own data race

Location: [Log.cpp:64](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/src/Log.cpp#L64).

- **What this is:** `level()` and `setLogLevel()` read and write a separate global `currentLogLevel`.
- **Problem:** That variable is not atomic or locked. Concurrent reads and level changes produced a ThreadSanitizer race; its initial `trace` value can also disagree with spdlog's actual initial level.
- **Fix:** Remove the duplicate state and read the logger's actual level, or synchronize the cached value and initialize it consistently. Keep `init()`/default-logger replacement restricted to a safe startup point: the dependency's raw-default-logger access explicitly does not support concurrent replacement. Relevant rule: CP.2.
- **If we skip it:** Runtime log-level changes introduce undefined behavior even though ordinary logging uses thread-safe sinks.

### 9. readFile can return success after a failed read

Location: [FileSystem.cpp:372](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/src/io/FileSystem.cpp#L372).

- **What this is:** The whole-file reader inserts an input stream's buffer into a string stream.
- **Problem:** `buffer << file.rdbuf()` records extraction failure on the destination stream, while the code checks `file.bad()` on the source. A fault-simulation filesystem subclass that lets a directory reach the read returned successful empty content; a path replacement between open and the directory check can expose the same route.
- **Fix:** Read through operations that update the input stream's state, such as a checked read loop, and return an error on an actual read failure. Preserve successful empty-file reads; simply treating every empty stream-buffer insertion as an error would reject valid empty files.
- **If we skip it:** A failed read can become empty or partial content with a successful `Result`, hiding the original I/O failure.

### 10. ThreadPool is publicly available but submit does not compile

Locations: [ThreadPool.hh:40](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/include/kcore/runtime/ThreadPool.hh#L40),
[ThreadPool.cpp:17](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/src/runtime/ThreadPool.cpp#L17).

- **What this is:** This is the already documented unfinished worker pool, preserved during extraction.
- **Problem:** Even `pool.submit([] { return 42; })` fails to compile: the capture lambda is const, but `packaged_task::operator()` is not. Independently, `enqueue` discards its task, workers are never started, and their `run()` methods are empty.
- **Fix:** Keep this facility explicitly unavailable until its queue, workers, shutdown, and task tests are implemented, or complete that implementation before consumers use it. Adding `mutable` fixes only the first compiler error.
- **If we skip it:** Consumers cannot use the advertised submission interface. This is known unfinished work, not a regression introduced by the split.

## Should fix: incorrect results, incomplete contracts, and generic API gaps

### 11. JSON numeric overflow escapes the Result interface

Location: [Json.cpp:8](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/src/serialization/Json.cpp#L8).

- **What this is:** `parseJson` returns parser failures as `Result<Json>`.
- **Problem:** Only `Json::parse_error` is caught. Input `1e1000` throws `Json::out_of_range.406`, which escaped the function in the probe.
- **Fix:** Catch the JSON library's relevant exception base for input-conversion failures and return `jsonParsingError`, preserving the detail. Allocation failure need not be disguised as malformed input. The dependency documents numeric-overflow exceptions in its parse interface.
- **If we skip it:** Untrusted numeric input can throw through code that handles parse failure exclusively through `Result`.

### 12. Numeric environment parsing silently accepts invalid values

Location: [Env.hh:20](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/include/kcore/io/Env.hh#L20).

- **What this is:** `getEnv<T>` converts environment strings into numeric settings.
- **Problem:** The conversions do not check how much input was consumed. The probes parsed `42junk` as `42` and unsigned `-1` as `18446744073709551615`.
- **Fix:** Require complete consumption, reject negative input for unsigned settings, and define the treatment of whitespace. `from_chars` or checked `sto*` end positions can enforce that contract.
- **If we skip it:** Mistyped or negative configuration values can silently become valid-looking limits, sizes, or timeouts.

### 13. Collecting a profile during an open region prints a timestamp as a duration

Locations: [Profiler.cpp:97](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/src/Profiler.cpp#L97),
[Profiler.cpp:40](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/src/Profiler.cpp#L40).

- **What this is:** A begin event temporarily stores an absolute clock count in the same vector later used for elapsed times.
- **Problem:** If a summary arrives before the end event, that raw timestamp is reported as elapsed time. The probe printed an “open region” duration of `845325326.050ms`, then lost the region after clearing its unmatched begin event.
- **Fix:** Separate open-region bookkeeping from completed durations and retain unfinished regions across snapshots, or reject collection while any region remains open. Fixing the data race in #7 alone does not fix these results.
- **If we skip it:** Profiles can contain enormous false durations and omit real work spanning a summary boundary.

### 14. SignalHandler leaves signals blocked after it is destroyed

Locations: [SignalHandler.cpp:12](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/src/runtime/SignalHandler.cpp#L12),
[SignalHandler.hh:17](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/include/kcore/runtime/SignalHandler.hh#L17).

- **What this is:** Construction blocks SIGINT and SIGTERM in the calling thread.
- **Problem:** The previous mask is discarded and there is no restoring destructor. The probe measured SIGTERM unblocked before a scoped handler and still blocked after it was gone.
- **Fix:** Save/restore the previous thread mask if this is a scoped resource. If permanent process setup is intended instead, expose/document that contract, including construction before worker threads and same-thread use; check POSIX return codes too. Relevant rule: R.1.
- **If we skip it:** Code after a scoped handler may stop responding to termination signals as expected, with no remaining waiter to consume them.

### 15. Calling start twice terminates the process

Location: [Thread.cpp:40](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/src/runtime/Thread.cpp#L40).

- **What this is:** `start()` replaces the stored `std::thread` with a newly created one.
- **Problem:** Replacing a still-joinable thread invokes `std::terminate`, even if that worker has already finished but has not been joined. A second `start()` reproduced process termination.
- **Fix:** Check the state before creating the new worker and define a clear failure policy: return an error or deliberately assert a documented precondition. Keep start/join ownership on one controlling thread.
- **If we skip it:** A duplicate lifecycle call causes abrupt termination rather than a diagnosable state error.

### 16. Lazy evaluation rejects ordinary lvalue and mutable callables

Location: [Functional.hh:181](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/include/kcore/Functional.hh#L181).

- **What this is:** `lazyEvaluate(F&&)` presents a generic callable interface.
- **Problem:** Passing a named lvalue lambda fails deduction, and a mutable lambda passes the advertised invocability condition but fails the `const F` result expression. Separate compile probes reproduced both failures.
- **Fix:** Store a decayed callable with correct forwarding and make the constraint, result type, and actual invocation agree on constness. Add lvalue and mutable-callable compile tests. Relevant concern: T.10.
- **If we skip it:** Routine generic callers cannot use the helper even though their functions are invocable.

### 17. unwrap cannot unwrap Result<void>

Location: [Unwrap.hh:10](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/include/kcore/Unwrap.hh#L10).

- **What this is:** `unwrap` asserts success and returns the result's value.
- **Problem:** `unwrap(Result<void>{})` instantiates `std::move(*result)` with a void expression and fails to compile. `Result<void>` is otherwise a normal library result type.
- **Fix:** Handle `void` explicitly with `if constexpr`, or add an overload that checks success and returns without a value.
- **If we skip it:** Callers need special handling for successful operations with no return value.

### 18. Flag helpers do not preserve normal enum operator semantics

Locations: [Enum.hh:28](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/include/kcore/Enum.hh#L28),
[Enum.hh:40](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/include/kcore/Enum.hh#L40).

- **What this is:** The helpers provide opt-in bit operations for enum classes.
- **Problem:** `|=` and `&=` return by value, so `auto& updated = (flags |= bit)` fails to compile and chained updates lose normal compound-assignment behavior. Also, `checkFlag` accepts a different enum type for its second argument and silently compares numeric bits across unrelated domains.
- **Fix:** Return `T&` from compound assignments and require matching enum types for both arguments to `checkFlag`. Relevant rule: C.160.
- **If we skip it:** Generic flag code fails unexpectedly, and unrelated flag families can be mixed without a type error.

### 19. Wrapper hashes promise noexcept even when the wrapped hash throws

Location: [Core.hh:103](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/include/kcore/Core.hh#L103).

- **What this is:** Hash specializations forward to `std::hash<T>` for a generic wrapped type.
- **Problem:** Both specializations unconditionally declare `noexcept`. A valid custom underlying hasher that throws therefore terminates the process through `Wrapper`/`Tag`; the probe's surrounding catch never received the exception.
- **Fix:** Make `noexcept` conditional on the underlying call or remove it. Test a custom hashable type with a throwing hasher. Relevant concern: F.6; the [standard permits program-defined hash specializations to throw](https://eel.is/c++draft/unord.hash).
- **If we skip it:** Wrapping a type changes recoverable hash failures into process termination.

### 20. Erased/base destruction requirements are not enforced

Locations: [InterfaceMap.hh:17](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/include/kcore/containers/InterfaceMap.hh#L17),
[Ref.hh:25](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/include/kcore/Ref.hh#L25).

- **What this is:** `InterfaceMap` erases derived objects into `unique_ptr<Interface>`, while `Ref` is designed to be inherited from but has a public nonvirtual destructor.
- **Problem:** An interface with virtual methods but no virtual destructor is accepted by `InterfaceMap`; destroying the map deletes through that unsafe base type. The probe observed zero derived-destructor calls. Deleting a derived `Ref` through `Ref<T>*` has the same C++ lifetime problem. These are interface-contract hazards; Anchor's inspected adapter interfaces already have virtual destructors.
- **Fix:** Require safe virtual destruction for interfaces used with derived registrations. For `Ref`, choose whether base deletion is supported and enforce that choice with virtual destruction or a base-only protected destructor; the latter would also require revisiting the current direct-`Ref` use. Relevant rule: C.35.
- **If we skip it:** An otherwise compiling new consumer can skip resource cleanup and invoke undefined behavior through the library's public ownership interfaces.

## Build, tests, and standards assessment

Read [CMakeLists.txt](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/CMakeLists.txt),
[kcoreConfig.cmake.in](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/cmake/kcoreConfig.cmake.in),
[conanfile.py](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/conanfile.py),
[tests/CMakeLists.txt](https://github.com/nekoffski/kcore/blob/1c9a829797d4aebbaf2548e5045513359b3620c5/tests/CMakeLists.txt),
both package-consumer build files, the package consumer,
and all 21 library test translation units plus their fixtures. The extraction's
package/consumer validation remains useful, but it does not exercise the unsafe
concurrency/lifetime cases above. The 83-test baseline was rerun during this audit.

The library already uses several sound practices: RAII containers, scoped locks,
`expected` for ordinary failures, checked partial writes, predicate-based condition
variable waits, and explicit ownership in the interface registry. It does **not**
yet meet the intended lifetime/concurrency safety level for a reusable foundation
library. The evidence is stronger than a style review: it includes actual invalid
memory access, races, escaped input errors, and accepted or rejected generic
instantiations with surprising behavior.

Two low-impact cleanup observations were left out of the numbered findings:
duplicate numeric helpers and unused profiler traversal scaffolding. No dependency
removal is recommended on the evidence collected. In particular, replacing the
callable wrapper with a standard alias must wait for supported library availability
or an explicit toolchain-baseline change.

Verdict: fix the lifetime and shared-state defects first; keep ThreadPool unavailable
until it works. Then address input/error handling and the smaller generic API gaps.

Not checked: Linux execution, other compiler/standard-library combinations,
process/plugin boundaries with independently linked copies of kcore, exhaustive
allocation/disk-failure injection, long-duration stress testing, or third-party
dependency security. `clang-tidy` was not available; Core Guidelines assessment was
manual and backed by the targeted probes described above. No fixes were applied.
